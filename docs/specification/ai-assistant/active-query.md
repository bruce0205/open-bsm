# 主動查詢

## Status

Proposed。本文定義使用者主動呼叫 AI 助手、上下文自動查詢、自然語言補充查詢與候選字提交流程。

## Problem Statement

使用者可能知道某個字或詞的語意，但不知道如何拆成 Boshiamy 字根。主動查詢應先利用目前輸入位置的上下文嘗試推論；若上下文不足以產生合適結果，再讓使用者以自然語言補充描述，並將描述與前文語境一併交給 AI 消歧。

## User Experience

1. 使用者在文件中將游標放在要輸入的位置。
2. 使用某個 hotkey 主動呼叫 AI 助手。
3. OpenBSM 開啟主動查詢視窗，並立即使用目前可取得的上下文呼叫 AI API。
4. 查詢期間顯示 loading 狀態，避免使用者誤以為查詢視窗沒有回應。
5. 若初始查詢回傳合適結果，顯示最多 `5` 個依可能性排序的候選字。
6. 若初始查詢沒有合適結果，包含 empty response，顯示自然語言輸入欄位。
7. 使用者輸入描述後，OpenBSM 將描述與前文語境一併放入 Prompt，再次呼叫 AI API。
8. 顯示最多 `5` 個依可能性排序的候選字。
9. 使用者明確選取候選字後，才將結果提交至目前 App。

## Query Flow

```text
Hotkey
  ↓
開啟查詢視窗
  ↓
以上下文自動查詢 ── loading ──┬─ 有合適結果 → 顯示候選字
                               └─ 無結果／空白 → 顯示描述輸入欄位
                                                  ↓
                                        描述 + 上下文查詢
                                                  ↓
                                            顯示候選字
                                                  ↓
                                            使用者提交
```

初始上下文查詢不應要求使用者先輸入自然語言描述。自然語言描述是初始查詢沒有合適結果時的 fallback 流程。

## Prompt Contract

自然語言補充查詢應同時傳送使用者描述與前文語境：

```text
使用者不知道某個字怎麼拆碼，用自然語言描述：「{desc}」
前文語境：{preceding_context}
請優先參考前文語境，推論這可能會是哪些字，依據可能性高低排序，並回傳前 5 個候選字。
```

實際實作時，Prompt 組合器應將使用者描述、上下文與輸出格式分開處理，避免未信任內容改變系統指令。若沒有可取得的前文，應保留 Prompt 結構並使用空的上下文欄位，或依 Provider contract 省略該欄位。

## Functional Requirements

1. 必須提供明確的 hotkey 或等效操作啟動主動查詢。
2. 查詢視窗開啟後，必須先以上下文自動發起一次 AI API 請求。
3. 初始請求期間必須顯示 loading 狀態。
4. 初始請求若回傳合適結果，直接顯示候選字，不要求使用者輸入描述。
5. 初始請求若回傳空白或沒有合適結果，必須提供自然語言描述輸入流程。
6. 自然語言查詢必須將描述與前文語境一併放入 Prompt。
7. 查詢結果最多顯示 `5` 個候選字，並依可能性排序。
8. 使用者必須明確選取候選字後，結果才能提交。
9. 查詢失敗、無結果或回傳格式錯誤時，不得影響既有輸入狀態。

## Technical Requirements

- 初始上下文查詢與自然語言補充查詢應使用可區分的 request／response 狀態。
- UI 應能表達 `loading`、`needs-input`、`showing-results`、`empty`、`error` 與 `cancelled` 狀態。
- Provider 回應應經過格式驗證，只接受符合預期的候選字資料。
- 查詢期間若使用者移動游標、切換 App 或開始新的 composition，回應應視為過期。
- 每個請求應攜帶上下文版本或等效識別值，避免舊回應覆蓋新狀態。
- 提交 AI 候選字時，應使用一般文字提交流程，不直接修改文件內容。
- UI 與輸入法主流程不得同步等待 API 回應。

## Edge Cases

- 初始上下文無法取得：仍可開啟查詢視窗；應直接進入自然語言描述流程，不能讓查詢失敗。
- API 延遲：顯示 loading；若使用者已切換文件、移動游標或開始新的 composition，回應抵達後直接丟棄。
- API 回傳空白：視為沒有合適結果，進入自然語言描述流程。
- API 回傳沒有合適候選：視為沒有合適結果，進入自然語言描述流程。
- 使用者未輸入描述：不送出第二次查詢，或顯示可理解的輸入提示。
- API 回傳超過 `5` 個候選：只顯示前 `5` 個有效候選。
- API 回傳格式錯誤：視為查詢失敗，不提交任何文字。
- 使用者取消查詢：關閉查詢 UI，不改變目前文件內容。
- 使用者在第二次查詢期間修改描述：舊請求回應不得覆蓋新描述的查詢狀態。

## Privacy and Security

- 初始查詢與自然語言查詢都應明確界定要傳送的前文範圍。
- Local Provider 為預設優先方案；Cloud Provider 必須由使用者明確啟用。
- Prompt、前文與 API 回應不可在一般日誌中以明文完整記錄。
- 使用者提供的描述與前文應視為不可信輸入，不能直接覆寫系統層級指令。
- 查詢失敗時，不應為了診斷而將完整上下文或 API 金鑰寫入日誌。

## Acceptance Criteria

- 使用者按下 hotkey 後，查詢視窗會開啟並立即進入 loading 狀態。
- 初始上下文查詢有合適結果時，會直接顯示最多 `5` 個候選字。
- 初始查詢為 empty 或沒有合適結果時，使用者可輸入自然語言描述。
- 第二次查詢會同時使用描述與前文語境，並顯示最多 `5` 個排序後候選字。
- AI 候選字只能由使用者明確選取後提交。
- 失敗、取消、無前文或過期回應都不會改變目前文件內容。

## Open Questions

- 主動查詢的 hotkey 是否需要提供使用者自訂？
- 初始上下文查詢的「合適結果」應由 Provider、信心門檻或本地驗證器判斷？
- 前文擷取是否需要依 App 能力提供不同策略？
- AI 回傳候選字是否應同時回傳對應的 Boshiamy 字根與解釋？
